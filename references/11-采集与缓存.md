# 11 · 采集与缓存：把「查询＝现场抓取」换成「查询＝读采集结果」

> 这份文档回答一个问题：**一条查询要等 20 秒，而且平台一挂就答不出来，怎么改？**
> 答案不是"把脚本优化得快一点"，而是换一个更根本的形状 —— **采集归采集，查询只是读**。
> 这是整套方案里性价比最高的一次改动：改动小、收益大，而且**失败时反而更可靠**。

## 1. 先算一笔账（决定要不要做）

真实项目的改造前基线：

| 命令 | 现场抓取耗时 |
|---|---|
| 余额（四个账号一起查） | 20.4s |
| 订单异常 | 13.5s |
| 门店营业情况 | 2s |

代价有两个，第二个比第一个严重得多：

1. 群里每问一次等 20 秒，同事会以为机器人坏了；
2. **平台挂了 / 登录态过期 → 查询直接失败**，而"今天没人查"和"系统坏了"在群里长得一模一样。

改完的样子：**1–4ms 返回**，并且平台挂着的时候，仍然答得出上一次成功的数据（带数据时间与陈旧提示）。

**判断标准**（满足两条就值得做）：

- 数据本身不需要秒级实时（余额、门店状态、当日累计 —— 分钟级足够）；
- 查询频率 ≥ 数据变化频率（"想起来看一眼"的场景基本都成立）；
- 同一份数据既被定时播报、又被随手查（那就更该只采一次）。

**反过来，这些情况别用**：数据必须实时（"此刻在线客服数"）；脚本本身很快（< 1 秒，缓存省不下什么）；
数据变化比采集周期还快（采到就已经过期）。

## 2. 落地：只改配置，不改脚本

三步，不动一行取数脚本：

```jsonc
{
  "collect":  { "enabled": true, "everyMinutes": 10, "startDelaySeconds": 30 },
  "freshness": { "staleMinutes": 30, "maxAgeMinutes": 180 },
  "history":  { "enabled": true, "keepDays": 14, "graceFactor": 2.5 },

  "commands": [
    {
      "id": "balance", "label": "账户余额",
      "snapshot": "balance",              // ← 就加这一行
      "match": ["余额"],
      "exe": "${PYTHON_EXE}", "args": ["-X", "utf8", "bot.py", "check", "--preview"]
    }
  ]
}
```

1. 给命令加 `"snapshot": "<源名>"`（源名是文件名，随便起，别用路径分隔符）；
2. 确认 `collect.enabled` 是 true；
3. 重启常驻进程加载配置，然后先手动采一轮：`run-fastlane.cmd --collect`（不发群）。

> 建议**一条一条地上**：先拿最慢的那条（通常是余额）验证路径，再铺其余源。
> 每条源之间互不影响，未配 `snapshot` 的命令行为**一字不变**。

**验收四条**（也就是自检该覆盖的东西）：

| 验什么 | 命令 | 期望 |
|---|---|---|
| 采得到 | `--collect [源]` | 退出码 0，`snapshots\<源>.json` 出现 |
| 读得快 | `--query <命令>` | 「读缓存」+ 端到端 **个位数毫秒** |
| 带时间 | 同上 | 正文首行 `> 数据时间：HH:MM（N 分钟前）` |
| 坏也能答 | 见 §6 的破坏性演练 | 查询仍毫秒返回 + `⚠️ 数据已 N 分钟未更新` |

## 3. 机制：一次采集与一次查询各发生了什么

**采集路径**（守护进程内置，`collect.everyMinutes` 一轮）：

```
[通道层] 定时器到点
   ├─ 对每条带 snapshot 的命令：跑它的「只打印」模式（与查询用的是同一套 exe/args）
   │    └─ 注意：复用 extractPayload()，分隔线提取 / dropLines / 剥 <font> 只有一份实现
   ├─ 写 snapshots\<源>.json         （临时文件 + rename 原子替换，读侧永远看到完整版本）
   ├─ 追加 history\<源>\<日期>.jsonl （append-only，一行一条）
   └─ 轮结束后：陈旧判定 → 该出声就推一条告警
```

**查询路径**（群里发一条命令）：

```
[通道层] 命中命令
   ├─ 有 snapshot 字段？
   │    ├─ 读 snapshots\<源>.json
   │    │    ├─ 有正文 且 数据时间没超过 freshness.maxAgeMinutes → 用它
   │    │    │    （最近一次采集失败也照答 —— 这正是缓存的主要收益）
   │    │    └─ 没有 / 太旧 → 落回现场抓取
   │    ├─ 按群作用域裁剪（快照存的是**未裁剪**原文，见 §4）
   │    └─ 正文首行加「数据时间」，超过 staleMinutes 再加一行陈旧警告
   └─ 返回（缓存命中时连"正在取数…"占位都不需要）
```

四条设计决定，每条都有理由：

| 决定 | 为什么 |
|---|---|
| 缓存**渲染后的 markdown**，不是结构化数据 | 改动最小、复用全部现有脚本（它们本来就有"只打印"模式）；代价是"改文案要重采一次"——手动跑一次 `--collect` 就抹平 |
| 快照存**未裁剪**的原文 | 裁剪是按群做的，采集那一刻并不知道将来会被哪个群查 |
| 快照写入用**临时文件 + rename** | 原子替换；否则查询侧可能读到半个 JSON |
| 历史用 **append-only jsonl** | 进程被强杀最多丢最后一行；而"读-改-写"一个 JSON 文件一旦写坏就是当天全丢 |

## 4. 四个必须说清的边界（别指望它做不到的事）

1. **平台通常不给历史查询。** 余额是"当前值"、门店是"当前营业状态"、订单是"截至现在"的累计 ——
   所以"补采"在这套里只能是**本地留档 + 空档可见**，**不是**回平台把中间那两小时的数据补出来。
   想把这句话变成假话，唯一的路是拿到平台的开放 API（选路优先正式 API，见 `07`）。
2. **首采之前没有缓存。** 这时查询会走现场抓取，行为与改造前完全一致 —— 不会答不出来，但也不会变快。
3. **采集器挂在常驻进程里，不是独立计划任务。** 常驻进程停，采集也停（看门狗 1 分钟内会把它拉起来）。
   为什么这么设计：注册计划任务需要管理员权限，而常驻进程本来就活着，生命周期正好落在
   「看门狗 + 心跳带 pid」这套已验证的机制里。想改成系统任务：`collect.enabled=false` +
   右键以管理员身份运行 `assets\注册采集任务.cmd`。
4. **缓存让"旧"成为可能，所以必须让新鲜度可见。** 数据时间写进正文、陈旧时加警告、超线推告警、体检列年龄。
   一句话：**缓存必须配一条"它有多旧"的出口**，否则就是把静默失败请进门。

## 5. 三个真踩过的坑

### 坑 1 · 采集失败时也刷新了 `captured_at`

现象：某个源连续失败好几天，**陈旧告警一次都没触发**。
根因：把"上次**尝试**时间"当成了"**数据**时间"—— 失败也推进它，于是这个源看起来永远刚刚更新过。
修法：`captured_at` 的语义收紧为"**这份正文**是什么时候取到的"，只在采集成功时推进；
另外存 `last_attempt_at` 表示"上次尝试"。从未成功过就留空 → 年龄 = 无穷大 → 告警说"从来没有采集成功过"。

> 这个坑的危险之处在于它**制造**了我们本来要消灭的那类静默失败。

### 坑 2 · 要求"最近一次采集成功"才肯用缓存

现象：平台一挂，手里那份 5 分钟前的数据也不给用，查询直接失败 —— **正好丢掉缓存的全部收益**。
根因：判定条件写成了 `ok === true`，把"这份数据能不能用"和"最近一次采集成没成功"混为一谈。
修法：能不能用只看两件事 —— **有正文**、**数据时间没超过 `maxAgeMinutes`**；
正文里标明数据时间与陈旧程度，把"要不要信这份旧数据"交给看数据的人。

### 坑 3 · 陈旧告警推进了业务群

现象：技术故障（登录态过期）推到了业务群，同事一脸问号。
根因：照抄了"连续失败告警回推出事会话"的做法，但采集器**没有**"出事的那条会话"。
修法：`alerts.stale.chats` 默认只推运维群/自己的群，留空则只写日志。

> 附带一条：**保留期清理这种"会删文件"的逻辑必须实测**，而且要造"该删 / 不该删"两组样本
> （过期的、昨天的、今天刚写的、甚至未来日期的）。日期比较写反了会删掉全部留档，而且悄无声息。

## 6. 验收与自检（都离线、都不发群）

| 命令 | 验什么 |
|---|---|
| `--collect [源]` | 真采一轮（联网取数、不发群），落快照 + 写历史 |
| `--query <命令> [--as-group <群ID>]` | 离线预演群内渲染：读缓存 → 按群裁剪 → 加数据时间。与线上查询走**同一段代码**，所以它可信 |
| `--stale-selftest` | 陈旧告警判定状态机（喂样本：未过线 / 刚过线 / 冷却中 / 冷却已过 / 从未成功） |
| `--history [源] [--date YYYY-MM-DD]` | 某天每轮采到了什么、哪个时段是空档 |
| `--check` | 缓存策略、陈旧告警策略、每条源的数据时间与年龄 |

**破坏性演练**（做完记得恢复配置）：把某条命令的 `exe` 指到一个不存在的路径，
再把它的快照数据时间伪造成 2 小时前，然后重启常驻进程。期望同时看到四件事：

1. 采集日志如实报失败（含原因），别的源照常成功；
2. 陈旧告警**真的推到了群**；
3. 同一时刻查这条命令：**毫秒返回**旧数据 + `> 数据时间：…（2 小时前）` + `⚠️ 数据已 N 分钟未更新`；
4. 快照文件里 `captured_at` 没被推进、`last_attempt_at` 推进了、`markdown` 保留上次成功那份。

## 7. 日常看什么（放进体检）

- **采集器**开没开；
- 每条源的「**数据时间（年龄）+ 最近一次成功/失败 + 今日留档 N/M 轮成功**」；
- 超 `staleMinutes` → WARN；超 `maxAgeMinutes` → BAD（此时查询会回退现场抓取）。

## 8. 一页速查

| 配置 | 位置 | 默认 | 作用 |
|---|---|---|---|
| `snapshot` | 单条命令 | 无 | 有它＝这条命令走读缓存 |
| `collect.enabled` / `everyMinutes` | 顶层 | true / 10 | 采集器开关与周期 |
| `collect.startDelaySeconds` | 顶层 | 30 | 启动后多久第一次采（先让长连接稳定） |
| `freshness.staleMinutes` | 顶层（可被命令覆盖） | 30 | 超过就加陈旧警告 |
| `freshness.maxAgeMinutes` | 顶层（可被命令覆盖） | 180 | 超过就不用缓存、回退现场抓取 |
| `history.enabled` / `keepDays` | 顶层 | true / 14 | 历史留档开关与保留期 |
| `history.graceFactor` | 顶层 | 2.5 | 空档判定倍数（相邻两次成功 > 周期×倍数） |
| `alerts.stale.*` | 顶层 | 开启 | 陈旧告警：`afterMinutes` / `cooldownMinutes` / `chats` / `dryRun` |

目录：`snapshots\<源>.json`（最新一份，查询用）· `history\<源>\<日期>.jsonl`（每天一个，回看用）
· `logs\collect.log`（采集器日志，与查询日志 `fastlane.log` 分开写）
