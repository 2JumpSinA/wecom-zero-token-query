# 06 · 安全与边界

开放给同事之前，先把这张表想清楚。**能力上限 = 你放进命令表的脚本**，通道本身没有任何额外能力。

## 机制

| 机制 | 作用 |
|---|---|
| 命令表写死 | 只有 `commands.json` 里列出的命令能跑；其它内容只会得到一条帮助 |
| 只读脚本 | 通道没有"写数据 / 执行任意命令"的能力 —— 你能查到什么，取决于你放了什么脚本 |
| 三级白名单 | 人（`allowedUsers`）× 群（`allowedChats`）× 命令（`chats`），越界一律拒绝 |
| 非白名单静默 | 名单外的人 @ 它**不给任何回应**，不暴露机器人存在 |
| `allowAllUsers` 默认关闭 | 配置里写 `true` 才会对所有人开放；默认"白名单为空 = 谁都不响应"，不会因为忘配而意外裸奔 |
| 无模型参与 | 命中靠精确匹配，不存在"被话术绕过去"的可能 |
| 凭证不出机器 | secret 只存本机文件/环境变量，不进入任何对话 |
| 单实例保护 | pid + 心跳双重校验，避免同一机器人挂两条连接造成消息重复 |

## 开放前必须确认的三件事
1. **你放进去的脚本能查到什么，别人就能看到什么。**
   涉及个人隐私、精确金额、身份信息的脚本，别放进命令表 —— 或者做成只返回聚合值。
2. **只读，不写。** 任何会修改数据、发送通知、触发下游动作的脚本都不要放。
   本通道没有二次确认机制，一发即执行。
3. **secret 是密码。** 不要贴进聊天、截图、提交到 git。
   `commands.json` 可以外发（里面只有 botId 和 ID 类信息），`secret.txt` 不行。

## 与 agent 通道的边界

- 本通道**不做**自由提问、多步推理、跨系统编排 —— 那些交给 agent（会消耗 token，但能力完整）
- **不要**为了"省一个机器人"而让两者共用同一个机器人：@ 一次两边都会收到 →
  群里双回复，而且 agent 照样起一轮、token 照花
- 建议的群内约定：`@数据查询` 走固定查询，`@AI助手` 走自由提问，各自职责清晰

## 建议的运维习惯

- 命令表改动后跑 `--routes` 和 `--selftest` 再重启
- 定期看 `logs\fastlane.log` 里有没有陌生 userid 在试（说明白名单配错了）
- 换了机器人或 secret 就更新 `secret.txt`，旧 secret 在后台作废
- 备份整个目录（含 `commands.json` 与 `secret.txt`），`logs\` 可不备

## 对所有人开放（`allowAllUsers: true`）时，边界在哪里

如果一个机器人**只是固定查询入口**（不是 agent 的 API、不能执行任意命令），
那么"谁能发消息"确实不是主要风险 —— **风险从「谁能用」转移到了「命令表里有什么」**。

开放时真正要守的是这三条：

1. **命令表只放只读脚本。** 一旦放进会写数据、会发通知、会触发下游动作的脚本，
   "对所有人开放"立刻从无害变成危险。`--check` 现在会对**没有预演开关**的命令给出提示。
2. **新增命令 = 扩大一次边界。** 别因为是"自己加的"就跳过确认。
3. **输出内容要先过一遍。** 脚本能查到什么，群里所有人就能看到什么；
   敏感字段要么别查，要么只返回聚合值。

反面例子（不要这样）：把「重启服务」「清理数据」「发测试消息」这类脚本放进命令表 ——
那等于给了群里每个人一个远程按钮。

> 一句话：**开放的正当性来自于命令表的克制**，而不是来自于"机器人很安全"这个模糊的印象。
