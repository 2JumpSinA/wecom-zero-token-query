# 00 · 架构总览：三层 + 一个契约

> 这份文档回答一个问题：**把「企微零 token 查询」这件事，怎么拆成可以分别复用的三层？**
> 之前那版是"某台机器的完整实现"，这一版把它拆成：**取数层 / 通道层 / 部署层**，
> 三层之间只靠一份「脚本契约」耦合。

## 1. 三层与职责边界

```
┌─────────────────────────────────────────────────────────────────────┐
│  第一层：取数层（Data Acquisition）                                  │
│  职责：从数据平台把数据拿下来，变成一段可读文本                        │
│  形态：任意语言、任意框架的脚本（Python / Node / PowerShell / 甚至 curl）│
│  通用性：★☆☆☆☆  —— 每个平台都不同，这一层天然不通用                   │
│  可复用的东西：选路决策树（07）+ 脚本契约（08）+ 凭据管理（09）         │
└───────────────────────────────┬─────────────────────────────────────┘
                                │  只通过「契约」耦合：见 §3
┌───────────────────────────────▼─────────────────────────────────────┐
│  第二层：通道层（Channel）—— 本方案的主体                            │
│  职责：收企微消息 → 匹配命令 → 跑脚本 → 把文本回群                    │
│  形态：常驻进程 + 命令表 JSON + 看门狗                                │
│  通用性：★★★★★  —— 与数据源完全无关，换脚本不用改一行代码            │
│  文档：01 企微侧准备 / 02 命令表与分群 / 10 泛化模型与作用域 / 05 排查  │
└───────────────────────────────┬─────────────────────────────────────┘
                                │  部署成一个「本机服务」
┌───────────────────────────────▼─────────────────────────────────────┐
│  第三层：部署层（Deployment）                                         │
│  职责：让它在别人机器上活下来 —— 环境、凭据、常驻、离线、升级          │
│  通用性：★★★★☆  —— 除了路径，没有任何机器特定内容                    │
│  文档：04 常驻与防闪窗 / 09 本地化部署 / scripts/install.ps1           │
└─────────────────────────────────────────────────────────────────────┘
```

**为什么这么切**：三层各自变化的原因不同 ——
数据平台会改版（第一层变），企微接口会改（第二层变），机器会换（第三层变）。
把它们分开，改一层不会牵动另外两层。

## 2. 数据流（一次查询的完整生命周期）

```
群里 @数据查询 订单
        │  ← 企微服务器把消息推到本机的长连接上（出站连接，不需要公网）
        ▼
[通道层] 解析：谁发的 → 在哪个群 → 命中哪条命令
        │
        ├─ 白名单/群/命令级校验（越界 → 拒绝并给本群可用清单）
        ├─ 先回占位消息「正在取数…」（流式消息，同一条）
        ▼
[取数层] 用配置好的解释器 + 参数执行你的脚本（只读模式）
        │
        ├─ 脚本从平台取数（API / 私有接口 / 导出文件 / 浏览器自动化）
        └─ 打印文本（契约：夹在两条 ==== 之间）
        ▼
[通道层] 取正文 → 剥 HTML 标签 → 按作用域裁剪（可选）→ 裁剪长度
        │
        └─ 同一条消息补全结果
        ▼
[部署层] 全程留痕：logs\fastlane.log · heartbeat.txt · watchdog.log
```

## 3. 契约：三层之间唯一的耦合面

**任何语言、任何来源的脚本，只要满足这四条，就能接进通道**（详细版见 `08`）：

| # | 契约 | 为什么 |
|---|---|---|
| 1 | **只读或可预演**：提供 `--preview`（或 `--dry`／不带 `--send`）开关，带上它绝不下发、绝不写状态 | 否则同一份数据会推两次；手动查询还会顶掉定时播报 |
| 2 | **正文可提取**：结果夹在两条 `====`（≥10 个等号）之间，或整段 stdout | 让进度日志和正文分开 |
| 3 | **退出码有语义**：0 = 成功；非 0 = 失败且把原因写出来 | 通道据此决定回"结果"还是回"失败详情" |
| 4 | **无交互、有超时**：不等待输入，单次运行有上限 | 群里没人能按回车 |

> 契约是**这一版最关键的通用化**：有了它，"支持什么数据平台"这个问题就消失了 ——
> 平台由你的脚本决定，通道只认契约。新增一个平台 = 新增一个满足契约的脚本 + 一段配置。

## 4. 通用性从哪来（诚实版）

| 部分 | 通用吗 | 说明 |
|---|---|---|
| 通道层代码 | ✅ 完全通用 | 与数据源零耦合；换脚本只改 JSON |
| 命令表 / 作用域模型 | ✅ 通用 | 「品牌」只是"维度"的一个实例，见 `10` |
| 部署与自愈 | ✅ 通用 | 计划任务 + 看门狗 + 心跳，任何 Windows 机器一样 |
| 脚本契约 | ✅ 通用 | 四条约束与平台无关 |
| **具体取数脚本** | ❌ **不可能通用** | 每个平台的登录态、接口、字段都不同 —— 这是本方案的成本所在 |
| 取数选路 | 🟡 半通用 | 决策树通用（`07`），但落地要针对具体平台 |

**所以正确的预期是**：这套东西把"**接入一个新查询**"的成本从"几天"降到"几十分钟"（写脚本 + 填配置 + 跑一次自检），
而不是"零成本支持任何平台"。任何声称后者通用的方案，都是在隐藏第一层的成本。

## 5. 这一版相对上一版补了什么（你点出的遗漏）

| 缺口 | 补法 |
|---|---|
| 只讲"我怎么做"，没讲"遇到别的平台怎么选路" | 新增 `07-取数路径.md`：决策树 + 五类平台配方 |
| 契约散落在说明里，没有校验手段 | 新增 `08`：契约成文 + `--probe` 探针（自动生成配置并校验输出） |
| 部署假设了"我的目录、我的解释器" | 新增 `09` + 配置**变量展开**（`${HERE}` `${DSH_HOME}` `${USERPROFILE}`），并给出可移植性自查表 |
| "品牌"写死在代码里 | 新增 `10`：泛化为**维度/作用域**（品牌、渠道、区域、账号都只是维度值） |
| 没讲清"为什么不能更通用" | 本文 §4 |
| 没讲凭据会过期这个最大运维痛点 | `09` 里给出凭据健康检查与失效告警的做法 |

## 6. 读法

- 想**理解整体** → 本文 + `SKILL.md`
- 想**接一个新平台** → `07`（选路）→ `08`（契约）→ 动手写脚本
- 想**在别人机器上装起来** → `scripts/install.ps1` + `09`
- 想**接进企微** → `01`（建机器人）→ `02`（命令表）→ `04`（常驻）
- 出问题 → `05`（排查）
