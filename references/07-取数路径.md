# 07 · 取数路径：遇到一个数据平台，该走哪条路

> 这一层天生不通用（每个平台都不同），但**选路的判断**是通用的。
> 原则：**从上往下试，成本递增**；能用接口就别抓包，能抓包就别开浏览器。

## 1. 先做判断：这个平台属于哪一类

| 类型 | 判断信号 | 建议路径 | 稳定性 | 接入工时 |
|---|---|---|---|---|
| **A 有正式 API** | 有开放平台/文档/AppKey；或公司中台提供接口 | 直接调接口（签名/token） | ★★★★★ | 0.5~2h |
| **B 只有后台网页，但有可复用私有接口** | F12 → Network 里能看到返回 JSON 的 XHR；页面数据是前端渲染的 | 抓包复现请求 + 复用登录态 | ★★★☆☆ | 2~6h |
| **C 只能导出文件** | 后台有"导出 Excel/CSV"，或每天收到报表邮件 | 导出/收信 → 落盘 → 解析 | ★★★★☆ | 1~3h |
| **D 平台能配推送/Webhook** | 有"消息订阅""回调地址""群机器人" | 本地接收 + 落库（注意：这是**事件**不是**查询**） | ★★★★☆ | 1~2h |
| **E 只有人眼能看** | 强反爬、验证码、必须登录客户端、接口签名算不出来 | 浏览器自动化（Playwright）—— **最后手段** | ★★☆☆☆ | 4~16h |

> 判断顺序很重要：很多人一上来就写浏览器自动化，那是成本最高、最脆的一条路。
> **先花 15 分钟做 A/B/C 的判断，能省下 8 小时。**

## 2. 每类的最小实现路径

### A · 有正式 API
1. 拿凭据（AppKey/Secret 或 OAuth token）
2. 直接 HTTP 请求 → 拿到 JSON
3. **必做**：把原始 JSON 存一份到 `data/raw/`，解析失败时能回看
4. 输出：把关键字段渲染成 markdown

坑：配额与限频（群里连点两次可能触发限流）；分页要写全；时区（平台多用 UTC 或北京时间，口径要写进输出）。

### B · 私有接口（最常见的"中台/后台"）
1. F12 → Network → 筛 XHR/Fetch → 找到返回业务数据的那条
2. 右键 **Copy as cURL** → 贴给 agent → 让它翻译成 Python `requests`
3. **登录态是全部难点**，按优先级选：
   - **浏览器 token 复用**（最稳）：从已登录浏览器里取 token，脚本只带 token 请求，**不调用登录接口** → 不会把网页端挤下线
   - **账号密码登录**：会挤掉网页端登录；频率高还会触发风控
   - **Cookie 注入**：cookie 过期快，维护麻烦
4. **失效要能被识别**：响应里出现"未登录/401/跳登录页"时，脚本必须**明确报错**（"凭据过期，请重新注入"），
   而不是静默返回 0 条 —— 群里看到"0 家门店"比看到报错危险得多

### C · 导出文件
1. 固定导出目录（或邮件附件落盘目录）
2. 解析：`.xlsx` 用 `openpyxl`/`pandas`，`.csv` 注意编码（GBK vs UTF-8）
3. **台账要做"已知项剔除"**：导出表里往往混着已闭店/测试店，脚本要维护一份"已知非异常"清单，
   否则群里天天报同一批假异常 —— 报警疲劳比不报警更糟

### D · 平台推送
1. 配置回调地址 → 但**回调需要公网入口**，本方案的"零公网"前提会被打破
2. 更现实的做法：**推送到企微群机器人（webhook）**，再由本地脚本定期把群里/库里的记录汇总
3. 适合"事件流"，**不适合"我现在要查一下"** —— 后者仍然要靠 A/B/C

### E · 浏览器自动化
1. 只在 A/B/C 都不成立时用
2. 用持久化 user-data-dir 保存登录态，减少重复登录
3. **必须**：设置单次超时、失败重试上限、并发上限（浏览器实例很贵）
4. 预期：页面改版即失效 —— 要有一个"脚本自检"能在群里/日志里暴露它坏了

## 3. 三条与平台无关的工程要求

### 3.1 凭据要有生命周期管理（这类系统最大的运维痛点）
- 存哪：优先系统凭据管理器（Windows Credential Manager / `keyring`）；退而求其次**加密文件**加权限；**绝不进 git、绝不进群**
- 怎么知道过期了：脚本里做**显式探测**（拿一个已知存在的样本去查，查不到就报"凭据可能失效"）
- 过期了怎么办：报错信息里**写清去哪续**（"运行 `login.bat` 重新注入"），而不是抛一个 traceback
- 建议：把"凭据健康检查"做成一条独立命令（例如 `状态`），群里随时能问一句

### 3.2 先落盘，再渲染
```
取数 → data/raw/<日期>.json（原始，排错用）
     → 解析 → 结构化
     → 渲染 → 群里的那几行
```
只存渲染结果的话，文案一改就要重新取数；改口径时没法复盘。

### 3.3 口径写进输出
任何"今日/近1小时/累计"都必须**由脚本打印出来**（`> 统计时段：今日 00:00 起，截至 12:39`）。
群里看到数字却不知道口径，等于没有数据；而且不同脚本口径不一致时，一眼能看出矛盾。

## 4. 输出格式约定（与通道层对齐）

| 要求 | 做法 |
|---|---|
| 正文可提取 | 夹在两条 `====`（≥10 个等号）之间 |
| 企微 markdown 子集 | `###` 标题、`>` 行、`**加粗**`；**不要用 `<font color>`**（智能机器人不认，会长出裸标签） |
| 单条长度 | < 20KB（超了会被截断）；明细落盘，群里只发汇总 |
| 失败可读 | 非 0 退出码 + 一行"人话"原因（不要只丢 traceback） |

## 5. 一页速查

```
拿到一个新平台，先问三句：
  1) 有没有正式 API？            → A，直接用
  2) 后台网页的数据是不是 XHR？   → B，抓包 + 复用 token
  3) 能不能导出/收报表？         → C，解析文件
都否 → D（事件流，不适合查询）或 E（浏览器自动化，最后手段）

无论走哪条，最后必须落在同一个契约上：
  只读/可预演 · 正文可提取 · 退出码有语义 · 无交互有超时   → 见 08
```

## 6. 可跑的样板（对应上面 A/B/C 三类）

| 样板 | 对应类型 | 内置的实战模式 |
|---|---|---|
| `examples/adapter-api.py` | A 正式 API | HMAC 签名、access_token 缓存、429 退避、业务码→人话 |
| `examples/adapter-private-api.py` | B 私有接口 | **token 注入优先于账号登录**、参数 AES 加解密、`重新登陆/401` 失效识别、重试退避 |
| `examples/adapter-export-file.py` | C 导出文件 | 列名映射（不用列号）、GBK/UTF-8 自适应、已知非异常台账剔除、缺列显式报错 |

三个都支持 `--demo` **离线跑通链路**，每个文件里标了 4~5 处 `TODO`。
用法与经验总结见 `examples/README.md`。
