# 03 · 脚本接口约定

通道只做三件事：**解析命令 → 跑脚本 → 把脚本输出的正文贴回群里**。
所以脚本必须满足三条约定，否则会出现"数据重复推"或"群里出现裸标签"。

## 约定一：只打印、不推送

脚本**绝不能**自己往群里发消息。否则：脚本先推一条 → 通道再把同一份内容贴回 @ 的消息 → **同一份数据在群里出现两次**，而且分不清哪条是谁发的。

做法：给脚本加一个开关（`--preview` / `--dry` / 不带 `--send`），带上它时：

- 只把文案打印到 stdout
- **不发送任何消息**
- **不写任何"今天已推"状态文件** ← 这条最容易漏：有的脚本会用 `.shop_report_date` 这类文件记录"今天推过了"，
  一次手动查询会把当天 09:00 的定时播报顶掉
- 失败时也不要借机发失败告警，更不要占用"同类失败 N 小时只提醒一次"的去重额度

**参考实现（Python）**：

```python
PREVIEW = False  # --preview：只打印不发送

def send_to_wecom(key: str, md_text: str) -> dict:
    if PREVIEW:
        print()
        print("=" * 40)
        print(md_text)
        print("=" * 40)
        return {"errcode": 0, "errmsg": "preview: 未发送"}
    # ... 正常发送逻辑 ...

def push_report(cfg):
    md = build_report(cfg)
    send_to_wecom(cfg["webhook_key"], md)
    if not PREVIEW:                 # ← 状态文件只在真正发送后才写
        mark_pushed_today()
    print("[已生成]" if PREVIEW else "[已推送]")
    return md

def main():
    global PREVIEW
    PREVIEW = "--preview" in sys.argv
    ...
```

**回归测试**（`assets/_preview_check.py` 就是干这个的）：把 `requests.post` 换成会抛异常的哨兵，
断言 preview 模式下**零 HTTP 请求**、且状态文件未被改动；同时断言非 preview 时**仍然会真的发送**。
改完脚本跑一次，比人肉检查可靠。

## 约定二：正文夹在两条 `====` 之间

通道默认按"取最后两条 `=`（≥10 个）分隔线之间的内容"抓正文，这样脚本的进度日志、
耗时统计这些噪声会被自动丢掉：

```
=== 1) 拉取数据 ===            ← 噪声，被丢弃
拉取完成，共 136 家
========================================   ← 分隔线
### 门店营业情况播报
> 项目：某某品牌
> 统计数据……
========================================   ← 分隔线
[done] 退出码 0              ← 噪声，被丢弃
```

要丢掉的分隔线之间的杂行（如 `--- 第 1/2 条 ---`、`[订单已推送]`），用 `dropLines` 正则过滤。

## 约定三：企微 markdown 的能用与不能用

| 语法 | 群机器人 webhook（定时推送） | **智能机器人（本通道）** |
|---|---|---|
| `###` 标题 / `>` 引用 / `**加粗**` | 支持 | **支持** |
| `<font color="info\|comment\|warning">` | 支持 | **不支持 → 原样显示成裸标签** |

所以脚本里**不要用 `<font>` 颜色标签**。想要强调就用 `**加粗**` 或 `⚠️` 这类符号。

> 通道会兜底剥掉这类标签（保留里面的文字），但你不会得到颜色 —— 所以不如脚本侧就别写。
> 定时播报走的是 webhook，颜色照旧生效；两条通道的 markdown 能力不同，这点必须记住。

## 退出码与错误

- 成功：退出码 0，正文完整
- 失败：非 0 退出码 + 错误信息打到 stdout/stderr —— 通道会把退出码和 stderr 尾部贴回群里，方便现场定位

## 取材清单（给 agent 生成脚本时必须有）

1. 脚本的完整路径
2. 用哪个解释器（绝对路径）
3. 完整命令行（含 `--preview` 之类的开关）
4. 脚本单次耗时（决定 `timeoutMs`）
5. 是否依赖登录态 / 缓存（需要时说明怎么续期）
